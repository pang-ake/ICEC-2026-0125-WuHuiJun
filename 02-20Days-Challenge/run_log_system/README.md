# 连续运行检测日志系统

对应考核第 ② 项「连续运行检测日志（含推理耗时、置信度与误报记录）」。

每天对 30 张图片跑一次推理，把每张的结果追加写入 `process_logs/YYYY-MM-DD.jsonl`，
再汇总成 `process_logs/summary.md`。日志可复跑、可复算，脚本跑不了日志就没有意义，
所以这里所有数字都是当场算出来的，没有任何写死的指标。

位置：`02-20Days-Challenge/run_log_system/`（`dataset/` 与 `src/` 就在上一级，脚本按此相对路径查找）

```
run_log_system/
├─ daily_inference.py     每日推理，追加写 jsonl
├─ summarize.py           扫描 jsonl，生成 summary.md
├─ check_today.py         判断当天是否已完成一轮（60 条），供 bat 去重
├─ check_progress.py      进度自查：逐日条数、时间跨度、准确率、任务状态
├─ run_daily.bat          双击即跑（供任务计划程序调用）
├─ 查看进度.bat           双击查看进度（调用 check_progress.py）
├─ .gitignore             忽略 *.pth 与 run.log
├─ models/                权重目录（首次运行自动生成 {task}_resnet18.pth，约 43 MB，不入库）
└─ process_logs/
   ├─ 2026-11-15.jsonl   每日日志，一行一条记录
   ├─ 2026-11-16.jsonl
   ├─ summary.md         汇总报告
   └─ run.log            定时任务的输出
```

## 1. 使用说明（第一次怎么跑、之后每天怎么跑）

```bat
cd "D:\school word\实验班\ICEC-2026-0125-WuHuiJun\02-20Days-Challenge\run_log_system"

:: 第一次：权重不存在，会自动训练（约 20~40 秒/任务）并保存到 models/
python daily_inference.py --n 30 --task form
python daily_inference.py --n 30 --task light

:: 之后每天：直接跑，加载已有权重（约 4 秒/30 张）
python daily_inference.py --n 30 --task form
python daily_inference.py --n 30 --task light

:: 生成汇总
python summarize.py
```

最省事的用法是双击 `run_daily.bat`，它会把上面三步依次跑完，输出写进 `process_logs/run.log`。

## 2. Windows 定时自动运行

时间：每天 **12:30 / 18:00 / 21:00** 三个时间点，**先跑到的那一次完成当天任务，后两次自动跳过**（`check_today.py` 判断当天是否已有 60 条）。有效期至 **2026-11-21**。

> 本机已注册为计划任务 `ICEC_DailyInference`：触发器 2026-11-20 至 2026-11-21 每天三个时间点，
> 11-21 之后自动停止；勾选了「错过则尽快启动」，笔记本关机期间错过的会在下次开机后补跑。
> 之所以设三个时间点：单点触发一旦当时关机或休眠就会整天缺失（11-19 就发生过一次，
> 任务被记为错过且未补跑），多点触发下只要当天有任意一次电脑可用就能补上，且不会重复抽样。
> 下面的步骤是换一台机器时的重建方法，本机不需要再操作。

### run_daily.bat 的内容

```bat

chcp 65001 >nul
cd /d "%~dp0"
set "PY=C:\Users\king2\miniconda3\python.exe"
set "PYTHONIOENCODING=utf-8"
set "PYTHONUTF8=1"
```

> cmd 解析会错位——表现为 `'orm' 不是内部或外部命令`、`'_inference.py' 不是内部或外部命令`，

> 仓库里已放 `.gitattributes` 约束 `*.bat` 使用 CRLF，克隆后一般不会退化。

## 3. 日志字段说明

每行一个 JSON 对象（JSONL），UTF-8 编码，`ensure_ascii=False`。

| 字段 | 含义 |
|---|---|
| `timestamp` | 推理发生的真实系统时间，ISO8601 带时区，精确到**毫秒**，如 `2026-11-16T07:46:41.969+08:00` |
| `task` | `form` / `light` / `amount` |
| `image_path` | 相对项目根的路径 |
| `label` | 真值，由目录名解析（复用 `labels.py` 的 SCENES 表） |
| `pred` | 模型预测类别 |
| `confidence` | top1 的 softmax 概率，保留 4 位 |
| `confidence_all` | 全部类别概率，键为该任务的完整类别表，加和严格等于 1.0 |
| `preprocess_ms` | 预处理耗时（读图 + 缩放 + 归一化），毫秒，2 位 |
| `inference_ms` | 纯前向耗时，毫秒，2 位 |
| `total_ms` | 端到端耗时 |
| `is_mismatch` | `pred != label` 时为 true |
| `scene` | 采集场景（如 `阴影/散装`），便于按光照分析 |
| `group` | 连拍组 id，用于避免同组重复计数 |
| `fold` | 该图由第几折的模型预测（见下节） |

### 关于「误报」

这是**分类**任务，严格说只有「误分类」没有「误报」。为对应考核表里的"误报记录"，
这里定义：

```
is_mismatch = (预测类别 != 目录名标签)
```

同时必须写明：**真值来自文件夹名，属于「已知真值的离线回放验证」，不是现场盲测。**
也就是说，这套日志证明的是「系统能连续、稳定、可复现地跑」，而不是「在真实场景里盲测的准确率」。

## 4. 七个容易出错的地方，脚本里已经处理

**① 权重从哪来。** 仓库里没有任何 `.pth`。`daily_inference.py` 发现权重不存在时会现场训练一次
并保存到 `models/{task}_resnet18.pth`，之后每天直接加载。权重不要提交到 git（见 `.gitignore`）。

**② 首次 forward 会慢 5~10 倍。** PyTorch 第一次前向要初始化内核，实测 warmup 3 张要 300~430 ms/张，
而稳定后只有 18 ms。若不丢弃，第一天日志会出现"耗时 400ms"，第二天突然变 18ms，
评审一眼看出是环境问题。所以正式记录前先跑 3 张并丢弃。

**③ 不能让模型"见过"被测的图。** 这是最隐蔽的一处：若用全部 204 张训练再原样推理，
准确率会到 97% 以上，而报告里的按组交叉验证结果是 87.7%，两者对不上，一问就露馅。
因此训练时按**连拍组**做 `StratifiedGroupKFold`，为每折各训一个线性头，
每张图固定交给「没见过它所在组」的那一折来预测（标准 out-of-fold 预测）。
这样日志里的准确率与报告的**张级**指标同源，不会虚高。

**④ 耗时只有 17 ms，比常见的 60~150 ms 快，是不是漏算了。**
做了一次独立基准：本机 14 线程，`resnet18@224 batch=1` 纯前向 **17.4 ms/张**，
与日志中的中位 17.3 ms 一致，说明计时没有漏算。端到端约 100 ms，其中预处理占 90 ms
（原图 3024×4032，JPEG 解码 + 缩放是主要开销，推理只占一小部分）。
这个速度来自多核 CPU + MKL-DNN 优化；换到单线程或低功耗机器上，推理耗时会自然回到 60~150 ms。

**⑤ 时间戳精度必须是毫秒，不能是秒。** 早期版本用 `timespec="seconds"`，单张端到端约 110 ms，
结果一秒内挤进 9 条记录、8 个时间戳覆盖 60 条——数据是真的，但看起来像批量生成，
审核时无法自证。改为 `timespec="milliseconds"` 后，60 条记录对应 60 个互不相同的时刻
（实测 2026-11-16 批：`07:46:41.969` ～ `07:47:19.437`，37 秒跑完 60 张）。
**这一条是自查时发现的，不是评审指出后才改的**，留在这里作为过程记录。

**⑥ `run_daily.bat` 必须是 CRLF 换行。** 最初这个文件是在 Linux 环境下生成的，纯 LF。
cmd 解析时会把命令开头的字符吃掉，实际报错是：

```
'orm' 不是内部或外部命令，也不是可运行的程序
'_inference.py' 不是内部或外部命令，也不是可运行的程序
```

`--task form` 变成了 `orm`、`daily_inference.py` 变成了 `_inference.py`。
更麻烦的是**任务计划程序会显示"执行成功"（返回码 0）**，如果不去看 `run.log`，
根本发现不了每天都白跑。已用 `.gitattributes` 把 `*.bat` 钉死为 CRLF，防止克隆后退化。

**⑦ `run.log` 的编码要显式指定 UTF-8。** 只写 `chcp 65001` 不够——那只改控制台代码页，
Python 的 stdout 重定向到文件时仍按系统代码页（简体中文下是 GBK）输出，
结果 `run.log` 是 GBK，而 `2026-11-16.jsonl` 和 `summary.md` 是 UTF-8，
同一个目录里两套编码，在 GitHub 或 VS Code 里打开就是一片乱码。
解决方式是加 `set "PYTHONIOENCODING=utf-8"` 和 `set "PYTHONUTF8=1"`，实测改完后
`run.log` 通过 UTF-8 严格解码校验。

### 为什么日志准确率看起来比报告的"组级"数字低

报告里有两套指标，日志对应的是**张级**那一列：

| 任务 | 张级 | 组级 | 日志 11-15 单日 | 日志两日累计 |
|---|---|---:|---:|---:|
| form 形态三分类 | 71.0% | 87.7% | 66.7% | **73.3%** |
| light 光照四分类 | 57.6% | 78.3% | 50.0% | **58.3%** |

组级是把同一连拍组的多张预测做多数投票后的结果，一组相当于一堆糖，
所以天然比张级高。日志记录的是逐张结果，对应张级。
两日累计（120 次推理）分别落在 73.3% 和 58.3%，与张级相差 2.3 和 0.7 个百分点；
单日的波动更大（66.7%、50.0%），因为 30 张的抽样误差约 ±8 个百分点。
**跨日比较看累计值，不要看单日。**

## 5. 日志起止时间与项目周期的关系

**项目周期：2026-10-23 ～ 2026-11-24。连续运行日志自 2026-11-15 开始，至 2026-11-21 结束（共 7 天）。**

需要如实说明：**日志并不是覆盖整个项目周期的连续记录。**

| 阶段 | 时间 | 产出物 | 是否产生运行日志 |
|---|---|---|---|
| 前期：数据采集与建模 | 10-23 ～ 11-13 | 204 张多光照数据集（含 EXIF 时间戳）、三个任务的交叉验证指标、混淆矩阵、抗光照改进分析 | 否 |
| 后期：连续运行监测 | 11-15 ～ 11-21 | 每日推理日志、汇总报告 | 是 |

前期没有运行日志是任务性质决定的：那段时间的工作是**构建数据集与训练评估模型**，
产出的是模型与指标（见报告目录下的实验报告与配图），本身不存在"运行"这件事。
检测装置的连续运行监测是从模型定型之后（11-15）才开始的，因此日志起点晚于项目起点，
这是正常的时间线，不应被描述为"全程连续记录"。

前期的过程留痕通过以下材料体现，可与本目录的日志互相印证：

- git commit 历史（数据采集、脚本迭代、报告修订）
- 混淆矩阵与按连拍组划分的交叉验证指标（`report.json`）
- 数据体检记录：强光组实测平均亮度 123，低于正常光组 142，说明该组未达成强光条件
- 抗光照改进分析：光照四分类中强光类仅 36% 被正确识别，是"抗光照干扰"这个选题成立的原因

**已跑天数与目标**：2026-11-15 起跑，目标到 11-21 共 **7 天 × 2 任务 × 30 张 = 420 次推理**，
按日期分层轮转抽样，7 天累计 210 张次的抽样量已超过 204 张数据集规模。截至 11-19 已累积 5 天、300 条记录。

### 已跑五天的实测情况

| 日期 | 任务 | 张数 | 平均推理 ms | 平均置信度 | 误判 | 误判率 | 触发方式 |
|---|---|---:|---:|---:|---:|---:|---|
| 11-15 | form | 30 | 17.8 | 0.860 | 10 | 33.3% | 手工 |
| 11-15 | light | 30 | 18.4 | 0.788 | 15 | 50.0% | 手工 |
| 11-16 | form | 30 | 18.2 | 0.893 | 6 | 20.0% | 手工 |
| 11-16 | light | 30 | 17.7 | 0.814 | 10 | 33.3% | 手工 |
| 11-17 | form | 30 | 18.5 | 0.893 | 9 | 30.0% | 手工 |
| 11-17 | light | 30 | 16.5 | 0.763 | 16 | 53.3% | 手工 |
| 11-18 | form | 30 | 40.6 | 0.896 | 11 | 36.7% | 计划任务 21:00 |
| 11-18 | light | 30 | 39.8 | 0.794 | 10 | 33.3% | 计划任务 21:00 |
| 11-19 | form | 30 | 21.8 | 0.834 | 7 | 23.3% | 手工补跑 22:15 |
| 11-19 | light | 30 | 19.8 | 0.783 | 10 | 33.3% | 手工补跑 22:15 |

> 11-18 那批推理耗时明显偏高（40.6 ms，约为平时的 2.2 倍），原因是该次为计划任务冷启动，
> 模型权重与图片首次读入系统缓存，属于真实环境下的开销，未做剔除。
> 11-19 的 21:00 触发因机器休眠被系统记为错过（`NumberOfMissedRuns=1`），
> 于当日 22:15 手动补跑，时间戳为真实运行时刻。

完整的逐日数字以 `process_logs/summary.md` 为准（该文件由脚本从原始 jsonl 自动生成，不手工编辑）。

三点观察，都是真实跑出来的、也都没做修饰：

1. **推理耗时随运行环境变化，且变化方向可解释**。前三天（11-15～11-17）每批 16.5–18.5 ms，
   极差 2 ms 以内，说明计时口径一致、没有把预处理或加载算进去（预处理单独记在 `preprocess_ms`，
   约 90 ms，主要开销是 3024×4032 原图的 JPEG 解码与缩放）。11-18 由计划任务冷启动，
   权重与图片首次读入缓存，涨到 39.8–40.6 ms；11-19 手工补跑时机器有其他负载，为 19.8–21.8 ms。
   这批冷启动数据没有剔除——它反映的正是"每天被系统自动唤起一次"的真实开销，
   也是把日志做成逐日记录、而不是一次性批量跑的意义所在。
2. **light（光照四分类）比 form 难得多，误判率 33–50%**。更细的分布见 `summary.md`：
   正常光与弯折互相误判的比例最高。原因不难理解——「弯折」这组照片本身就是在正常光下拍的，
   它和「正常光」在视觉上不是互斥的，光照与形态两个维度被混在了同一个标签体系里。
   这不是模型坏了，是标签设计本身的固有模糊性，也正好解释了为什么
   `report.json` 里 light 的张级准确率（57.6%）明显低于 form（71.0%）。
