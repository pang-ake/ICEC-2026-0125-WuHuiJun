## 三、第三步：204 张原图 606 MB，推不推？

**我的判断：** 推原图。

**理由（自己推的，没听 AI 的折中方案）：**
1. 大纲项目二第 20 分项明确要"本人实拍不少于 200 张多光照数据集（含 EXIF 时间戳）"。压成 1600px 会重新编码 JPEG，这属于改动原始数据，在"诚信一票否决"的考核里不值得赌。
2. 204 张里单张最大 6.33 MB，远低于 GitHub 100 MB 硬限，技术上推得动。
3. 真正该排除的是 `糖果盘点数据集_提交包.zip`（603 MB），它和 `dataset/` 内容完全重复——排除重复件不算删数据。

**AI 一开始建议"压缩到 1600px 长边、保留 EXIF，约 40 MB 更快"**，我否掉了。这条记在这里，是因为它正是一个"看起来更工程化、实际会伤到证据链"的建议——压缩 JPEG 会重写量化表，严格说就已经不是原始采集数据了。代价是 push 慢，这个代价我认。

## 四、第四步：查 EXIF，发现一个真缺口

**AI 的检查命令与结果：**

```python
fs = sorted(glob.glob('model/dataset/*/*/*.jpg'))   # 204 张
# 前 100 KB 内含 'Exif' 标记的：108 / 204
```

**结论：只有 108 张保留 EXIF，其余 96 张的 EXIF 被微信导出流程剥掉了。**

这不是我能补的——补写 EXIF 就是伪造元数据。所以处理方式是：
- 文件名里的 `微信图片_20261114180505.jpg` 仍带 14 位拍摄时间戳，时间线可追溯；
- 在 `02-20Days-Challenge/README.md` 的"已知风险点"里明写"大纲 EXIF 一项只能部分满足"。

**经验：** 主动交代缺口，比让面试官翻出来再问要好。这条也写进了根 README 的诚信声明第 3 条。

## 五、第五步：process_logs 只有训练指标，不是逐日日志

`model/count_tool/runs/report.json` 是真实训练输出，但它是一次性评估指标，**不等于**大纲要的"连续运行检测日志"。

我一度想让 AI 直接生造一份像逐日日志的 JSONL——**这是错的，属于造假**。最终处理：`process_logs/README.md` 里如实写"当前状态 ❌ 非逐日累积"，并给出一段可用的打点代码，从今天起真跑真记。

## 六、沉淀下来的三条

1. **先找到规范页，再动手建目录。** 招生首页里的时间线、FAQ 都不含目录规范。
2. **重复件可以排除，原始数据不能改写。** 603 MB 的重复 zip 排除掉是清洁；重编码 606 MB 原图是伤证据。
3. **缺什么就写什么。** EXIF 缺 96 张、process_logs 不是逐日——两处都在 README 里明写，并给出补齐方法。这比"看起来完整"更能扛面试追问。
